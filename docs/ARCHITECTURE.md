# 统一后台架构约定

## 统一后台与 RBAC

`ruoyi-xxx-by` 系列统一采用一个后台应用、一个登录入口和一套账号体系，不单独拆分用户端和管理端。普通用户和管理员使用同一套布局与页面，根据角色动态加载菜单、路由，并控制页面、按钮和接口权限。

- 普通用户基础角色沿用现有标识 `common`。`admin` 自动继承启用且未删除的 `common` 角色的功能权限，再叠加自身显式授权的管理权限；无须在用户角色关联表重复分配 `common`。
- 多角色功能权限取并集。管理员可使用普通用户功能；普通用户不会反向继承管理权限。其他业务角色按实际授权工作，不能仅因登录就获得 `common` 的授权。
- 保留内置超级管理员（用户 ID 1）的全权限约定，`*:*:*` 是服务端给超级管理员的标记。普通账号仅持有名为 `admin` 的角色不会自动成为超级管理员，仍需配置该角色的管理权限。
- `getInfo.roles` 返回生效角色标识（含继承角色），`user.roles` 和角色编辑接口保留显式分配结果。菜单查询、动态路由和 API 使用同一套生效功能授权；前端角色指令和辅助函数只根据服务端的 `*:*:*` 判断超级管理员，不把 `admin` 角色名当作无限权限。
- 角色、菜单停用/软删除或撤销授权后，后续服务端请求重新读取授权并拒绝访问；重新获取用户信息及路由后前端同步。已打开页面可能暂时保留菜单，但不能绕过服务端校验。
- 功能权限继承不自动放宽数据范围。数据范围继续由显式分配角色和业务归属规则决定；个人资料、本人记录等功能必须使用当前登录用户身份，不能因管理员身份错误地读取另一用户的个人数据。
- 公共首页、登录、验证码和支付回调等按现有协议保留必要公开入口；它们不构成另一个用户端。新增普通用户功能也应加入现有后台菜单/路由体系，并在服务端定义权限和数据归属校验，不能用“非管理员才允许”排除管理员。

此调整不新增数据库表，不重写既有用户角色关系，也不把继承角色写回数据库。已有项目更新前后应检查 `common` 的菜单授权是否确实适合作为普通用户基础权限；示例种子不是实际业务的最小授权配置。

## 回归验证

管理员与普通用户共用登录和个人中心；验证生效角色、菜单、接口授权、单向继承、停用和撤销授权，以及超级管理员兼容行为。具体命令与实际结果见开发记录。
